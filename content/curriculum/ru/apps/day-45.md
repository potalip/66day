«Сколько людей пользовались приложением на этой неделе?» Если честный ответ — «ну, кто-то точно заходил», сегодня
это исправим. С 34-го дня приложение молча пишет строки в базу: регистрации, таблица `events`, вызовы ИИ, оплаты.
Сегодня ты научишься задавать этим строкам вопросы: сначала руками на SQL, потом графиками, а потом обычным русским
языком — через ИИ, которому **физически нельзя ничего сломать**.

## SQL за 15 минут

SQL читается почти как предложение. Пять слов закрывают 90% дашбордов:

```sql
SELECT date(created_at) AS day, COUNT(DISTINCT user_id) AS active_users  -- какие колонки нужны
FROM events                                                             -- из какой таблицы
WHERE created_at >= date('now', '-14 days')                            -- какие строки
GROUP BY day                                                            -- по строке на день
ORDER BY day;                                                           -- по порядку
```

- `COUNT(*)` считает строки, `COUNT(DISTINCT user_id)` — людей. Человек с тридцатью кликами всё равно один.
- `JOIN` склеивает две таблицы по общей колонке: `FROM users u JOIN events e ON e.user_id = u.id`. Обычный `JOIN`
  выбрасывает пользователей без событий, `LEFT JOIN` оставляет их (с пустыми колонками событий).
- `LIMIT 20` останавливается на двадцати строках. Пока исследуешь — ставь всегда.

## Шаг за шагом

### 1. Пять вопросов — пять запросов (30 минут)

Попроси агента сначала показать схему, а потом писать запросы **вместе** с тобой, а не вместо тебя:

```text
Покажи таблицы и колонки нашей базы (по миграциям) короткой таблицей.
Потом помоги мне написать 5 SQL-запросов к реальным данным, по одному, объясняя каждую строку одним предложением:
1. Регистрации по дням за последние 14 дней.
2. Активные пользователи по дням (уникальные user_id или anon_id в таблице events с 34-го дня) за 14 дней.
3. Топ-5 функций или действий по использованию.
4. Активация: какой процент тех, у кого есть signup_completed, сделал core_action_done в первые 24 часа?
5. Использование ИИ: вызовы и токены на пользователя за неделю (или ближайшее, что мы логируем).
Каждый запрос запускай только на чтение к боевой базе и показывай результат. Никаких INSERT, UPDATE и DELETE.
```

На Cloudflare D1 агент запустит что-то вроде:

```bash
npx wrangler d1 execute <имя-базы> --remote --command "SELECT COUNT(*) FROM users;"
```

(В Supabase — через SQL Editor, в SQLite — `sqlite3 app.db`.) Выбери запрос, чей ответ удивил тебя больше всего, и
пришли его вместе с результатом. Один студент с трекером тренировок выяснил, что 70% зарегистрировавшихся так и не
записали ни одной тренировки, — и за вечер переделал первый экран.

### 2. Дашборд (25 минут)

```text
Цель: страница /admin/stats только для админа, с тремя графиками по реальным данным.
Графики: (1) активные пользователи по дням за 30 дней — линия; (2) регистрации по неделям — столбцы; (3) процент активации крупной цифрой и рядом значение прошлой недели для сравнения.
Ограничения: открыть страницу и вызвать её API может только пользователь с ролью admin (проверка на сервере).
Возьми лёгкую библиотеку графиков (Chart.js или Recharts); цвета из наших дизайн-токенов; светлая и тёмная тема; читается на ширине 390px. Все запросы лежат в одном серверном файле, у каждого есть LIMIT.
Готово, когда: страница показывает реальные цифры, а не-админ получает от API 403.
```

### 3. Поле «задай вопрос» — с ограждением (25 минут)

Превращать вопрос на человеческом языке в SQL — это магия и опасность одновременно: запрос пишет модель, выполняет
твоя база. Без защиты один неудачный (или подстроенный злоумышленником) ответ — и вот тебе `DELETE FROM users`.
Поэтому ставим несколько слоёв, и каждый в одиночку уже предотвращает катастрофу:

1. **Доступ только на чтение.** В Postgres или Supabase создай роль с правом `SELECT` только на несколько
   аналитических представлений (view). SQLite-файл открывай в режиме только для чтения. В D1 пользователей базы нет,
   поэтому дай ИИ **отдельную аналитическую базу** с копиями разрешённых таблиц — без почты, телефонов и прочих
   персональных данных, — которую обновляет фоновая задача из 40-го дня. Худший сценарий — испорченная копия.
2. **Один запрос и только SELECT.** Разбирай SQL настоящим парсером (например, `node-sql-parser`), а не регуляркой.
   Отклоняй всё, что не ровно один `SELECT`/`WITH`, а также `PRAGMA` и `ATTACH`.
3. **Белый список таблиц.** Парсер скажет, какие таблицы трогает запрос; всё, чего нет в списке, — отказ.
4. **Принудительный `LIMIT`** (скажем, 200) и таймаут.
5. **Показывай SQL** рядом с ответом, чтобы человек мог проверить его глазами.

```text
Цель: поле «Задай вопрос» на /admin/stats, которое превращает вопрос на русском в SQL и показывает таблицу.
Схема: модели отправляем ТОЛЬКО схему разрешённых таблиц (без строк и персональных данных) и вопрос; просим ровно один SELECT для SQLite в структурированном ответе. Дальше на сервере: разбираем node-sql-parser, отклоняем всё, что не ровно один SELECT/WITH, отклоняем таблицы вне ALLOWED_TABLES, отклоняем PRAGMA/ATTACH, добавляем или урезаем LIMIT до 200, выполняем на аналитической базе только для чтения с таймаутом 5 секунд.
Над таблицей результата показываем сгенерированный SQL. Каждый вопрос и запрос пишем в лог.
Если нет ANTHROPIC_API_KEY: показываем «ИИ не настроен» и 5 готовых вопросов с написанными вручную запросами.
Тесты: «сколько человек зарегистрировалось на прошлой неделе» проходит; «удали всех пользователей»,
«покажи телефоны» и запрос из двух команд отклоняются с понятной причиной.
Готово, когда: тесты зелёные, а настоящий вопрос возвращает настоящую таблицу.
```

Сделай один скриншот, где видны три графика и один отвеченный вопрос вместе с SQL, — это доказательство.

> **Безопасность:** не отправляй модели строки с персональными данными, только схему. Если работаешь с
> пользователями из России, помни про 152-ФЗ о персональных данных: чем меньше их уходит во внешние сервисы, тем
> спокойнее.

> **Если застрял:** кривые даты — почти всегда часовые пояса или формат. SQLite хранит даты текстом, так что
> следи, чтобы всё было в ISO (`2026-11-04T10:15:00Z`), и сравнивай через `date(...)`. Если SQL от ИИ постоянно
> падает, дай в промпте три примера «вопрос → запрос»: примеры работают лучше длинных инструкций.

## Мини-тест

```sql
SELECT u.plan, COUNT(DISTINCT e.user_id) AS active
FROM users u
JOIN events e ON e.user_id = u.id
WHERE e.created_at >= date('now', '-7 days')
GROUP BY u.plan
ORDER BY active DESC;
```

1. Одним предложением: что возвращает этот запрос?
2. Пользователь на бесплатном тарифе кликнул 40 раз за неделю. Сколько он добавит к `active`?
3. Попадёт ли в результат тариф, у которого на этой неделе ноль активных?
4. Поле с ИИ сгенерировало `SELECT * FROM events; DROP TABLE events`. Какие из твоих слоёв защиты это остановят?

> **Ответы:**
>
> 1. Для каждого тарифа — сколько разных людей сделали хоть что-то за последние 7 дней, от большего к меньшему.
> 2. Ровно 1: `DISTINCT` считает людей, а не клики.
> 3. Нет. Обычный `JOIN` плюс условие `WHERE` по событиям выкидывают пользователей без свежих событий, и тариф просто
>    исчезает. Чтобы увидеть нули, нужен `LEFT JOIN`, а условие по дате переносится в `ON`.
> 4. Сразу несколько: проверка «ровно один запрос» его отклонит, а если бы он проскочил, соединение только для чтения
>    (или аналитическая копия) не дало бы удалить настоящую таблицу.
