Сейчас твоё приложение забывает всё, стоит нажать F5. Для макета нормально, для продукта — приговор: никто не станет
вести учеников в программе с амнезией. Сегодня файл с примерами уходит на пенсию, а его место занимает настоящая
база данных — сначала у тебя на компьютере, потом в интернете.

## Где живут данные

- **Память** (состояние React): мгновенно, но исчезает при перезагрузке. Годится для «что сейчас набрано в поле».
- **Хранилище браузера** (`localStorage`): переживает перезагрузку, но живёт в *одном* браузере на *одном* устройстве.
  Открыл приложение с телефона — пусто. Годится для настроек вроде темы.
- **База данных на сервере**: переживает всё, одинакова с любого устройства, её можно резервировать. Настоящим
  записям приложения место здесь.

Фронтенд никогда не ходит в базу напрямую. Он обращается к твоему **API** — бэкенду, знакомому по 11-му дню, — а уже
API говорит с базой. Четыре базовые операции называются **CRUD**: Create, Read, Update, Delete — создать, прочитать,
изменить, удалить. В HTTP это обычно `POST`, `GET`, `PATCH`, `DELETE` по адресам вроде `/api/lessons` и `/api/lessons/42`.

**Миграция** — маленький SQL-файл, который меняет структуру базы («создай таблицу lessons»). Миграции лежат в git,
поэтому у тебя на ноутбуке и в боевой базе всегда одинаковая структура.

**Два хороших пути** (выбери один и не меняй до 27-го дня):

- **Cloudflare D1** — SQLite в облаке, рядом с Worker'ом из 11-го дня. Щедрый бесплатный тариф; при локальной
  разработке используется настоящий файл SQLite. Рекомендуем.
- **Supabase** — Postgres с удобной панелью, хорошо дружит с Vercel, а на 24-й день даст готовую авторизацию.

> **Важно:** доступность облачных сервисов и способы оплаты зависят от страны. Бесплатные тарифы D1 и Supabase
> карту обычно не требуют; если регистрация у тебя не проходит, подойдёт и обычный SQLite на VPS
> (Timeweb Cloud, Selectel) — попроси агента адаптировать промпт.

## Шаг за шагом

### 1. База + CRUD API (50 минут)

```text
Цель: замени src/sampleData.ts настоящей базой данных и CRUD API.

Контекст: приложение описано в docs/SPEC.md (см. раздел «Данные»). Фронтенд — Vite + React + TS.
Используем Cloudflare Workers + D1: один Worker отдаёт собранный фронтенд и API по /api (возьми актуальную
настройку Cloudflare Vite plugin из документации). Для маршрутов можно Hono.

Ограничения:
- Схема — миграцией в migrations/0001_init.sql. У каждой таблицы id, created_at, updated_at.
- Эндпоинты: GET /api/<сущности>, POST /api/<сущности>, PATCH /api/<сущности>/:id, DELETE /api/<сущности>/:id.
- Проверяй входные данные на сервере (обязательные поля, максимальная длина) и возвращай понятные ошибки 400 в JSON.
- Только параметризованные запросы (никогда не склеивай SQL из строк).
- Фронтенд показывает загрузку, ошибку и вчерашнее пустое состояние, когда записей нет.
- Добавь скрипт «npm run db:migrate:local».

Сначала объясни план: схему (покажи SQL), эндпоинты и какие файлы тронешь. Дождись моего «ок».
В конце: примени миграцию локально, запусти приложение и докажи работу через curl — создай запись, получи список,
измени её, удали — и покажи каждый ответ. Потом скажи, что мне нажать в браузере, чтобы проверить самому.
```

Проверь в браузере: добавь две записи, обнови страницу — они на месте. Закоммить, запушь и вставь ссылку на коммит
на GitHub (на странице репозитория нажми на сообщение коммита).

> **Совет (путь через Supabase):** промпт тот же, только второй абзац замени на «Используй Supabase Postgres через
> официальный JS-клиент; таблицу создай SQL-миграцией; сервисный ключ держи только на сервере». Сверься с актуальной
> документацией Supabase.

### 2. Деплой с базой (40 минут)

Боевая база — отдельная пустая копия. Создаёшь её, применяешь ту же миграцию и деплоишь:

```bash
npx wrangler d1 create tutor-db              # один раз; выведет конфиг привязки, который нужно добавить
npx wrangler d1 migrations apply tutor-db --remote
npx wrangler deploy
```

Пусть агент сделает это вместе с тобой:

```text
Цель: задеплой приложение с удалённой базой D1.
Прежде чем запускать, перечисли точные команды и изменения в конфиге и дождись моего «ок».
После деплоя: через curl по боевому адресу создай одну запись и получи список, покажи вывод.
Потом скажи, как удалить эту тестовую запись.
```

А теперь главное доказательство: добавь запись с ноутбука и открой боевую ссылку на телефоне. Она там. Обнови.
Всё ещё там. Вот это уже продукт.

> **Если застрял:** «no such table» на боевом сайте значит, что миграцию применили локально, но не с `--remote`.
> Ошибка 500 без подробностей? Запусти `npx wrangler tail` во втором терминале, повтори ошибку и вставь лог агенту
> с припиской «сначала объясни причину, потом чини».

> **Безопасность:** твой API теперь публичный: любой, у кого есть ссылка, может добавлять записи. На сегодня это
> допустимо, а на 24-й день каждый пользователь будет видеть только свои данные. До тех пор не храни ничего личного —
> телефоны учеников и их родителей в том числе.

## Мини-тест

Что подходит для каждой задачи: память, `localStorage`, база данных или ничего из этого?

1. Текст, который человек набирает в поле «заметка», пока не нажал «Сохранить».
2. Предпочитает ли пользователь тёмную тему.
3. Список занятий, который нужен и на телефоне, и на ноутбуке.
4. API-ключ от ИИ-провайдера.

<details><summary>Ответы</summary>

1. Память (состояние компонента). Это временно, до сохранения.
2. `localStorage` подойдёт — это настройка конкретного устройства. (Позже её можно хранить в базе для каждого пользователя.)
3. База данных: должна переживать перезагрузку и быть одинаковой на всех устройствах.
4. Ничего из этого: это **секрет** на сервере (`wrangler secret put` или переменные окружения хостинга). Не в браузере,
   не в базе, не в git.

</details>
