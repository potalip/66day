У твоего приложения уже три живых пользователя. С этого момента баг — не твоя маленькая неприятность, а их испорченный
вечер. Агент за один запрос меняет десятки строк, и подход «потыкал — вроде работает» больше не годится. Несколько
тестов на Vitest у тебя уже есть с 18-го, 24-го и 26-го дней (схема, запасной разбор, утечка между аккаунтами,
подтверждение). Сегодня ты проверишь, что они вообще способны упасть, допишешь недостающие и натянешь страховочную
сетку, которая сама срабатывает на каждый пуш.

## Что такое тест на самом деле

Тест — это маленькая программа, которая вызывает твой код с известными данными и проверяет результат. Если кто-то
(ты, агент или ты же в час ночи) сломает это поведение, тест покраснеет раньше, чем заметят пользователи.

Ловушка с агентами: они охотно пишут **тесты, которые ничего не проверяют**. Тест, который подменяет (мокает) ту самую
функцию, что тестирует, или проверяет только `expect(result).toBeDefined()`, будет зелёным вечно и не защитит ни от
чего. Твоя работа — не писать тесты, а **решать, что тестировать, и убеждаться, что каждый тест умеет падать**.

Что тестировать, по порядку:

1. **Чистую логику с правилами**: расчёт цены, даты, лимиты, права доступа («может ли пользователь А менять запись Б?»).
2. **Парсеры и валидаторы**: код с 18-го дня, который превращает ответ модели в проверенный JSON. Корми его мусором нарочно.
3. **Один сквозной сценарий**: тест на Playwright, который открывает приложение, делает главное действие и видит результат.

Не трать время на стили, сторонние библиотеки и точные формулировки модели (они меняются от запуска к запуску —
проверяй *форму* ответа, а не слова).

> **Совет:** лучший приём дня. Когда тест прошёл, сломай код специально — поменяй `>` на `<`. Если тест остался
> зелёным, он бесполезен. Это называется мутационным тестированием, только вручную.

## Шаг за шагом

### 1. Выбери три вещи, которые стоит защищать (5 мин)

Открой проект с агентом и спроси, где риск:

```text
Цель: найти 3–5 функций в репозитории, которые больше всего стоит покрыть юнит-тестами.
Контекст: это моё основное приложение (фронтенд на React + Vite, API на Cloudflare Workers + D1, ИИ-функция со структурированным ответом). Часть тестов на Vitest уже есть: сначала перечисли их и скажи, какие не упадут никогда.
Ограничения: в приоритете чистые функции с бизнес-правилами, валидацией и разбором данных. Вёрстку не трогай.
Готово, когда: для каждой функции есть путь к файлу, чем баг в ней навредит пользователям, и 2–3 случая для проверки (включая один пограничный и один с неправильным вводом). Код пока не пиши.
```

Прочитай список. Вычеркни всё, что на деле проверяет библиотеку, а не твой код. Оставь три пункта.

### 2. Пусть агент напишет тесты (30 мин)

Приложение на TypeScript, значит, берём **Vitest**: он дружит с конфигом Vite. Если бот написан на Python (aiogram),
его тесты — на **pytest**.

```text
Цель: юнит-тесты для трёх функций, о которых мы договорились.
Контекст: Vitest, уже настроенный в этом Vite-проекте (pytest — только для бота на Python).
Ограничения:
- Не мокать функцию, которую тестируем. Мокать можно только сеть и API модели.
- Название каждого теста — правило простыми словами, например «не даёт перенести занятие на прошедшую дату».
- Для каждой функции минимум один пограничный случай и один неправильный ввод.
- Скрипт "npm test" запускает тесты один раз и выходит (vitest run), без watch-режима.
Готово, когда: npm test проходит локально, и ты показываешь мне вывод.
```

Потом запусти сам:

```bash
npm test
# вариант для Python:
pytest -q
```

Теперь мутационный трюк: попроси агента временно сломать одно правило, запусти `npm test` и убедись, что тесты
покраснели. Верни как было. Закоммить, запушь и скопируй ссылку на коммит в GitHub — это доказательство для задания 2.

> **Если застрял:** ошибки «Cannot find module» или про ESM обычно значат, что настройки тестов не совпадают с
> проектом. Отдай агенту полный текст ошибки с припиской «почини настройку тестов, код приложения не трогай». Если
> функцию невозможно протестировать, потому что она сама лезет в базу, попроси агента вынести правило в чистую
> функцию. Это не лишняя работа: так тесты улучшают архитектуру.

### 3. Один сквозной смоук-тест (по желанию, 15 мин)

```text
Цель: один тест на Playwright: поднимает dev-сервер, открывает главную, выполняет основное действие (например, создаёт запись) и проверяет, что она появилась.
Ограничения: в тестах только фолбэк/фикстуры вместо настоящего API модели. Не длиннее 40 строк.
Готово, когда: npx playwright test проходит локально.
```

### 4. CI на GitHub Actions (25 мин)

**CI** (continuous integration, непрерывная интеграция) — это чистый компьютер на стороне GitHub, который на каждый пуш
и пул-реквест ставит твой проект с нуля и гоняет тесты. Он лечит синдром «а у меня работает».

```text
Цель: workflow GitHub Actions в файле .github/workflows/ci.yml.
Контекст: Node-проект с npm test и npm run build. Возможно, есть тест на Playwright.
Ограничения: запуск на push и pull_request; актуальные мажорные версии actions/checkout и actions/setup-node,
Node 22 и кэш npm; шаги npm ci, npm test, npm run build.
Секреты не нужны: тесты работают на фикстурах, без настоящих ключей.
Готово, когда: файл закоммичен, и ты объяснил каждый шаг одной строкой.
```

Получится примерно так (агент может взять более новые мажорные версии actions — это нормально):

```yaml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm test
      - run: npm run build
```

Запушь, открой вкладку **Actions** в репозитории и посмотри, как идёт прогон. Зелёная галочка? Открой прогон и
скопируй его адрес — это доказательство для задания 3. Красный крестик? Кликни по упавшему шагу, скопируй лог и
отдай агенту.

> **Безопасность, на будущее:** если CI понадобится переменная окружения, добавляй её в
> `Settings → Secrets and variables → Actions`, а не в YAML. Сегодня секреты не нужны.

## Мини-тест

1. Тест подменяет `calculateTotal` моком и проверяет, что мок вернул 42. Польза есть?
2. ИИ-функция каждый раз формулирует ответ по-разному. Что проверять?
3. Тест прошёл. Как понять, что он вообще способен упасть?
4. CI зелёный, а живое приложение сломано. Назови одну вероятную причину.

> **Ответы:**
>
> 1. Нет. Он проверяет мок, а не твой код.
> 2. Форму: обязательные поля на месте, типы верные, длины в пределах, а на кривом ответе срабатывает фолбэк.
> 3. Сломать код нарочно и увидеть красный тест.
> 4. Тесты не покрывают этот сценарий, или настройки и секреты в продакшене отличаются от CI. Добавь тест ровно на то, что сломалось.

## Готово, когда…

- [ ] Понятно, почему тест, который не умеет падать, хуже, чем никакого.
- [ ] 3+ осмысленных теста проходят через `npm test` (или `pytest`), а нарочно сломанный код их краснит. Ссылка на коммит вставлена.
- [ ] `.github/workflows/ci.yml` запускается на пуш, ссылка на зелёный прогон вставлена.
- [ ] Мини-тест пройден.
