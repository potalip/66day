Сейчас любой, у кого есть ссылка, видит всех учеников, все суммы и все телефоны родителей — и может спустить твой
бюджет на ИИ. До 27-го дня, когда придут настоящие пользователи, это нужно прекратить. Сегодня ты добавляешь вход и, что
важнее, гарантируешь: вошедший человек может трогать только свои данные. А потом сам пытаешься взломать своё
приложение, чтобы это доказать.

## Сессии, cookie, OAuth, вход по ссылке

- **Аутентификация** отвечает на вопрос «кто ты?» — это вход.
- **Авторизация** — на вопрос «что тебе можно?»: «это занятие принадлежит пользователю 42, а ты 17, так что нет».
  Большинство реальных утечек — ошибки авторизации, а не взломанные пароли.
- **Сессия** — сервер помнит, что «этот браузер — пользователь 42». Обычно сессия хранится в **cookie** — маленьком значении,
  которое браузер отправляет с каждым запросом. Правильная сессионная cookie — `HttpOnly` (JavaScript её не прочитает),
  `Secure` (только https) и `SameSite` (не уходит с чужих сайтов).
- **OAuth** — это «Войти через Google / GitHub / Яндекс»: провайдер подтверждает личность, а ты вообще не держишь пароли.
- **Вход по ссылке** (magic link) — одноразовая ссылка на почту. Пароль нельзя ни забыть, ни слить.
- **Вход через Telegram** — для русскоязычной аудитории часто самый естественный вариант: у твоих пользователей
  Telegram и так открыт, а бот у тебя уже есть с 20-го дня. Telegram присылает данные пользователя с подписью, и сервер
  обязан эту подпись **проверить** (HMAC с ключом из токена бота) и убедиться, что данные свежие.

**Не пиши авторизацию сам.** Бери проверенное:

- **Telegram Login** + проверка подписи на сервере по официальной документации, плюс сессия через библиотеку.
- **Better Auth** — открытая библиотека внутри твоего бэкенда, работает с D1/SQLite (как подключить к Cloudflare
  Workers — смотри актуальную документацию).
- **Supabase Auth** — если ты на Supabase, он уже встроен.
- **Clerk** — готовый сервис с красивыми компонентами.

> **Важно:** вход через Google в некоторых странах работает с перебоями, а у части аудитории Google-аккаунта нет
> вовсе. Telegram или вход по ссылке на почту закрывают почти всех.

## Шаг за шагом

### 1. Вход и данные по пользователям (60 минут)

```text
Цель: добавь вход и привяжи каждую запись к пользователю.

Контекст: приложение из docs/SPEC.md; бэкенд на Cloudflare Workers + D1 (или Supabase). Вход: <Telegram Login |
Better Auth с входом по ссылке на почту | Supabase Auth | Clerk>. Следуй актуальной документации под наш стек.

Ограничения:
- Для Telegram Login: проверка подписи (hash) строго по документации Telegram, отказ, если auth_date старше суток; токен бота — только серверный секрет.
- Миграция: добавь user_id (NOT NULL) во все таблицы с пользовательскими данными. Старые анонимные записи — отдать моему аккаунту после первого входа (дай одноразовый скрипт), потом сделать user_id обязательным.
- Все маршруты API, кроме маршрутов входа, требуют действующую сессию, иначе 401.
- user_id ВСЕГДА берётся из проверенной сессии на сервере и НИКОГДА — из тела запроса, параметров или URL.
- Каждый запрос к базе фильтрует по user_id, включая изменение и удаление. Чужая запись — ответ 404 (не раскрывай, что она существует).
- ИИ-эндпоинты (/api/extract, /api/extract-media) — только после входа; дневные лимиты теперь считаются по user_id.
- Сессионная cookie: HttpOnly, Secure, SameSite=Lax. Видимая кнопка «Выйти».
- Невошедший видит короткую страницу: что делает приложение, и кнопку «Войти».

Сначала объясни план: какой провайдер и почему, SQL миграции, какие маршруты поменяются, какие файлы тронешь.
Дождись моего «ок». В конце выведи список всех маршрутов API с пометкой «нужен вход: да/нет» и покажи, как запрос curl без cookie получает 401.
```

Сохрани ключи провайдера как секреты (`wrangler secret put …`), задеплой и войди с телефона. Закоммить, запушь,
вставь ссылку на коммит.

> **Если застрял:** виджет Telegram пишет «Bot domain invalid» — в BotFather не задан домен: `/setdomain` → твой бот →
> адрес приложения. У других провайдеров вход, который возвращает на начало по кругу, почти всегда значит, что
> разрешённый адрес возврата в кабинете не совпадает с адресом приложения посимвольно (http и https, слэш в конце,
> localhost или продакшен). Вставь агенту точную ошибку и оба адреса.

### 2. Тест на двух аккаунтах (30 минут)

Теперь пробуем вломиться. Нужны два разных профиля браузера (или обычное окно и окно инкогнито) и два аккаунта —
например, твой Telegram и Telegram друга или вторая почта.

1. Как **A** создай запись. Открой инструменты разработчика → Network, нажми на запись и посмотри её id в адресе
   запроса (скажем, `/api/lessons/37`).
2. Как **B** открой список: записи A там быть не должно.
3. Как **B** попробуй прочитать, изменить и удалить запись A напрямую. Скопируй cookie B из инструментов разработчика
   (Application → Cookies) в переменную терминала — это пароль, больше никуда её не вставляй — и выполни:

```bash
read -rs B_COOKIE   # вставь имя=значение сессионной cookie и нажми Enter (ввод не отображается)
curl -i https://<твоё-приложение>/api/lessons/37 -H "Cookie: $B_COOKIE"
curl -i -X PATCH https://<твоё-приложение>/api/lessons/37 -H "Cookie: $B_COOKIE" \
  -H "Content-Type: application/json" -d '{"note":"взлом"}'
curl -i -X DELETE https://<твоё-приложение>/api/lessons/37 -H "Cookie: $B_COOKIE"
```

4. Попробуй создать запись как B, подсунув в тело `"user_id"` пользователя A. Это поле должно игнорироваться.

Каждый запрос должен вернуть **404** (или 401/403), а запись A — остаться нетронутой. Опиши, какие запросы отправлялись
и что пришло в ответ. Если что-то утекло — отличная находка, отдай агенту точный запрос и ответ:

```text
Уязвимость: пользователь B может <читать/менять> запись пользователя A. Запрос и ответ ниже.
Сначала объясни корневую причину, потом исправь везде, где встречается тот же шаблон, добавь тест на Vitest, который её воспроизводит, и снова прогони мои команды из теста на двух аккаунтах, чтобы доказать исправление.
```

> **Безопасность:** сессионная cookie равна паролю. Удали переменную из терминала после теста (`unset B_COOKIE`) и никогда не показывай
> cookie на скриншотах и в чатах.

## Мини-тест: аутентификация или авторизация?

1. Пользователь ввёл неверный пароль.
2. Пользователь B открывает `/api/lessons/37`, которое принадлежит A.
3. Сессионная cookie истекла за ночь.
4. Страницу со списком всех пользователей может видеть только владелец приложения.

> **Ответы:**
>
> 1. Аутентификация: приложение не может подтвердить, кто это.
> 2. Авторизация: B известен, но смотреть эту запись ему нельзя. Ответ — 404.
> 3. Аутентификация: сервер больше не знает, кто ты, — войди заново.
> 4. Авторизация: проверка роли («это владелец?») при каждом запросе к этой странице.
