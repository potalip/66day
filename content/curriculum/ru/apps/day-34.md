Сейчас ты гадаешь. Гадаешь, что приложение быстрое (на твоём ноутбуке и домашнем Wi-Fi). Гадаешь, что им удобно
пользоваться (мышкой и с идеальным зрением). Гадаешь, какая функция всем нравится. Сегодня меняем догадки на цифры:
оценку скорости, оценку доступности, реальные события и журнал, который скажет, когда что-то сломалось у другого человека.

## Три вещи простыми словами

**Скорость.** Человек со средним телефоном в метро решает за три секунды, ждать или закрыть. Lighthouse (встроен в
Chrome DevTools) имитирует ровно это и ставит оценку от 0 до 100. Обычные виновники: огромные картинки, тяжёлый
JavaScript, шрифты, блокирующие отрисовку, вёрстка, которая прыгает при загрузке.

**Доступность (a11y).** Примерно каждый шестой человек живёт с какой-то формой инвалидности, а «временно ограничен»
бывает каждый: яркое солнце, рука в гипсе, на другой руке ребёнок. Основы: настоящие кнопки (а не кликабельные
`div`), подписи у всех полей, достаточный контраст, видимая рамка фокуса, всё работает с одной клавиатуры, у картинок
есть `alt`.

**Измерения.** Два инструмента на два вопроса:
- *Аналитика*: «что делают люди?» Просмотры, регистрации, ключевое действие. Основа — **своя таблица `events`** в D1:
  одна строка на каждое значимое действие, пишет её маленький помощник `track()`. Данные твои, их можно спрашивать
  SQL-запросами (45-й день) и взять в финальный проект (54-й день). Дашборд поверх — по желанию: **Plausible** (без
  cookie, платный или на своём сервере) или **PostHog** (бесплатный тариф, хостинг в ЕС). Собирай минимум, без
  персональных данных.
- *Журнал ошибок*: «что сломалось, у кого и когда?» Ловишь ошибки фронтенда и упавшие запросы к API, хранишь, получаешь сигнал.

> **Важно:** Яндекс Метрика популярна и бесплатна, но с Вебвизором записывает действия пользователя целиком. Если
> берёшь её — выключи лишнее и честно напиши об этом в политике конфиденциальности. А если у тебя пользователи из
> России, помни про закон о персональных данных (152-ФЗ): чем меньше собираешь, тем меньше проблем.

## Шаг за шагом

### 1. Замерь «до» (10 мин)

Открой живое приложение в Chrome → DevTools → **Lighthouse** → Mobile → Analyze. Сделай скриншот четырёх оценок.
Или из терминала:

```bash
npx lighthouse https://your-app.example --form-factor=mobile --output=html --output-path=before.html --view
```

И пройди главный сценарий **только с клавиатуры**: Tab, Shift+Tab, Enter, пробел, Escape. Запиши, где застрял или
потерял фокус.

### 2. Исправь вместе с агентом (35 мин)

Дай агенту отчёт, а не ощущения:

```text
Цель: поднять оценки Lighthouse (мобильные) по Performance и Accessibility, не меняя функциональность.
Контекст: вот отчёт Lighthouse (вставляю непройденные проверки) и мои заметки по клавиатуре: <заметки>.
Ограничения:
- Картинки: правильные размеры, современные форматы, заданы width/height, ленивая загрузка ниже первого экрана.
- Тяжёлые маршруты — через динамический import; убрать неиспользуемые зависимости.
- Доступность: настоящие кнопки и ссылки, подписи у всех полей, контраст не ниже 4.5:1 в ОБЕИХ темах,
  видимые стили фокуса, диалоги удерживают фокус и закрываются по Escape, осмысленный alt.
- Автоматическая проверка: тест на Playwright с @axe-core/playwright для главных страниц, запуск в CI.
Готово, когда: каждое исправление привязано к конкретной проверке; CI зелёный.
```

Замерь ещё раз с теми же настройками и сохрани скриншот «после». Для задания 2 загрузи одну картинку, где «до» и
«после» стоят рядом. Не гонись за сотней: 90+ по доступности и заметный рост скорости — отличный день.

> **Если застрял:** Performance скачет от прогона к прогону — это нормально. Прогони три раза и возьми средний по величине результат (медиану). Если
> в тёмной теме падает контраст, попроси агента поправить цветовые токены один раз, а не каждый компонент по отдельности.

### 3. Аналитика + журнал ошибок (30 мин)

```text
Цель: бережная аналитика и журнал ошибок.
Ограничения:
- Таблица событий (миграция D1): events(id, user_id NULL, anon_id, name, props_json, created_at), индексы по
  (name, created_at) и (user_id, created_at). anon_id — случайный id в собственной cookie, чтобы считать и тех, кто
  ещё не зарегистрировался; при регистрации связать его с user_id.
- Серверный помощник track(name, props) внутри наших API-обработчиков плюс POST /api/events для событий только из
  фронтенда (принимает лишь имена из белого списка, с ограничением частоты). Упавший track() никогда не ломает запрос
  пользователя.
- Отслеживать ровно: session_started, signup_completed, core_action_done, ai_called (props: model, tokens, ms),
  upgrade_clicked. В props никогда нет почты, имён и текста сообщений.
- По желанию: дублировать те же события в Plausible ИЛИ PostHog (хостинг в ЕС, запись сессий и автосбор полей
  выключены), только в продакшене.
- Журнал ошибок: обработчики window error и unhandledrejection плюс middleware ошибок API шлют
  {message, stack (обрезанный), route, release, time} на POST /api/errors, хранение в таблице errors.
  Эндпоинт с ограничением частоты. Новый тип ошибки — одно сообщение мне в Telegram (helper из дня 31).
- Маленькая страница /admin/errors (только для владельца) с последними 50 ошибками.
- Одна простая фраза об аналитике в нашей политике конфиденциальности.
Готово, когда: я вызываю тестовое событие и тестовую ошибку и вижу оба, и работает запрос
SELECT name, COUNT(*) FROM events GROUP BY name.
```

Добавь скрытую тестовую кнопку или выполни в консоли браузера `setTimeout(() => { throw new Error("test from day 34") })`
(голый `throw`, набранный в консоли, до твоего обработчика не доходит). Потом сделай главное действие
и проверь, что оно записалось: `npx wrangler d1 execute <имя-базы> --remote --command "SELECT name, created_at FROM events ORDER BY id DESC LIMIT 5"`.
Для задания 3 вставь: пять названий событий, вывод этого запроса, дашборд (если подключил) и первую ошибку, которую увидел.

> **Совет:** Sentry — отраслевой стандарт для отлова ошибок с бесплатным тарифом. Не хочешь писать свой журнал — бери
> его, правила те же: никаких персональных данных, доступ только у владельца.

сделаешь из-за этого.
