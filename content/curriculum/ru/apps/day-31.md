Половина «автоматизаций», за которые платят, устроена так: *каждое утро посмотри на что-то и скажи мне, если это
важно.* Новые регистрации в приложении, курс валюты, свежие вакансии, вчерашние продажи. Никаких конструкторов со
стрелочками — у тебя уже есть бот (день 20) и бэкенд. Сегодня они начинают работать по расписанию.

## Три способа разбудить код

- **Cron (расписание)**: «запускай каждый день в 07:00». Синтаксис — пять полей: минута, час, день месяца, месяц,
  день недели. `0 7 * * *` — ежедневно в 07:00, `*/15 * * * *` — каждые 15 минут. Время почти всегда **по UTC**:
  07:00 UTC — это 10:00 по Москве и 12:00 по Астане.
- **Вебхук (событие)**: другой сервис сам дёргает твой адрес, когда что-то произошло. Твой Telegram-бот уже так живёт.
- **Опрос (polling)**: ты регулярно проверяешь источник сам. Cron + опрос — способ следить за тем, что не умеет слать вебхуки.

Где запускать:

- **Cron Triggers в Cloudflare Workers**, если бэкенд уже там: рядом с `fetch()` добавляешь обработчик `scheduled()`.
  Точно по времени, быстро, бесплатного тарифа хватает с запасом.
- **`schedule` в GitHub Actions**, если задача — скрипт в репозитории. Просто, но запуск может опоздать на минуты,
  а в неактивных публичных репозиториях расписание отключается через 60 дней.

### Вежливый парсинг

Если у источника есть API или RSS — бери их. Если приходится читать страницу: проверь `robots.txt` и правила сайта,
ходи не чаще раза в несколько минут, указывай `User-Agent` с контактом, кэшируй результат, не лезь за логин и не
собирай персональные данные. Вежливость ещё и практична: грубые парсеры быстро банят.

## Шаг за шагом

### 1. Реши, за чем следить (5 мин)

Выбери то, что полезно *тебе*, лучше всего из своего же приложения: «каждое утро присылай, сколько вчера было новых
пользователей и ИИ-запросов». Другие хорошие варианты: курс ЦБ выше порога (API cbr-xml-daily), новые вакансии по
запросу через открытый API hh.ru, новые посты в RSS.

### 2. Собери задачу (45 мин)

```text
Цель: задача по расписанию, которая каждый день в 07:00 UTC присылает мне сообщение в Telegram.
Контекст: задачу выполняет Worker основного приложения (Cloudflare Workers + D1), а не Worker бота с 20-го дня.
Секреты BOT_TOKEN и OWNER_CHAT_ID добавлены в основное приложение через wrangler secret put (локально — в .dev.vars).
Что проверять: <опиши, например: число новых пользователей и ИИ-запросов за последние 24 часа из D1>.
Ограничения:
- Cron-триггер в конфиге wrangler и обработчик scheduled(); логику вынеси в отдельную функцию runDailyReport(env), чтобы её можно было тестировать и запускать вручную.
- Отправка через sendMessage в Telegram на мой chat id (переменная OWNER_CHAT_ID). Коротко, цифры в начале.
- Если ничего не изменилось, всё равно пришли строку «всё спокойно» — так я вижу, что задача жива.
- Никаких секретов в коде и в файлах, которые попадут в коммит.
Готово, когда: я запускаю задачу локально и получаю сообщение в Telegram.
```

Сначала добавь два секрета. Свой chat id найдёшь в логах: бот с 19-го дня пишет chat id каждого сообщения, так что
отправь ему `/start` и посмотри id в `npx wrangler tail` (запусти его внутри `bot/`). Потом запусти задачу локально,
не дожидаясь семи утра: подними `npm run dev` и во втором терминале открой тестовый адрес на порту, который он вывел:

```bash
curl "http://localhost:5173/cdn-cgi/handler/scheduled?cron=0+7+*+*+*"
```

(У голого `wrangler dev` порт 8787. В старых настройках — `wrangler dev --test-scheduled` и адрес `/__scheduled`;
актуальный способ — в документации Cron Triggers.) Задеплой через `npm run build && npx wrangler deploy` и загляни в
панель Cloudflare: в разделе **Triggers** у воркера появится cron.

Делаешь на GitHub Actions? Агент создаст `.github/workflows/daily.yml` с `on: schedule: - cron: "0 7 * * *"` и
`workflow_dispatch:`, чтобы для проверки можно было нажать **Run workflow**. Токен бота — в секреты репозитория.

Для задания 2 вставь: cron-выражение, что проверяется, и сообщение, которое пришло, слово в слово.

> **Если застрял:** сообщение не приходит? Попроси агента логировать полный ответ Telegram. `chat not found` — неверный
> chat id или ты ни разу не нажал «Старт» в боте (бот не может написать первым тому, кто его не запускал).
> `401 Unauthorized` — неверный токен. (`getUpdates` тут не поможет: пока стоит вебхук с 20-го дня, он не работает.) В логах
> вообще пусто? Запусти `npx wrangler tail` во время вызова и посмотри, срабатывает ли обработчик.

### 3. Сделай надёжно и скучно (30 мин)

Задача, которая сработала один раз, — демо. Задача, которая работает каждый день целый год, держится на трёх вещах:

- **Повторы с паузой (backoff)**: сеть иногда падает. Три попытки с паузами 1, 4 и 16 секунд. Если Telegram ответил
  `429 Too Many Requests`, жди ровно столько секунд, сколько он указал в `retry_after`.
- **Логи**: одна строка на запуск — старт, что нашли, отправили или упали, сколько заняло. Последние запуски храни в
  таблице `job_runs`, чтобы на вопрос «а во вторник она отработала?» был ответ.
- **Идемпотентность**: два запуска не должны дать два сообщения. Дай каждому запуску ключ вроде
  `daily-report:2026-11-04` и храни его с ограничением уникальности. Ключ уже есть — пропускаем.

```text
Цель: сделать runDailyReport надёжной.
Ограничения:
- Сетевые вызовы — через helper повторов: 3 попытки, экспоненциальная пауза, уважать retry_after при 429 от Telegram.
- Таблица job_runs (run_key UNIQUE, started_at, finished_at, status, details). Сначала вставляем ключ запуска; если вставка упала из-за дубля — логируем «уже отправлено» и выходим.
- Одна структурированная строка лога (JSON) на запуск: длительность и результат.
- Тесты на Vitest: helper повторяет и в итоге успешен; второй запуск с тем же ключом ничего не отправляет.
Готово, когда: два запуска подряд дают ровно одно сообщение, тесты зелёные.
```

Запусти дважды. Пришло одно сообщение? Для задания 3 опиши: как устроены повторы, формат ключа запуска, где лежат логи.

> **Совет:** если задача упадёт *после* записи ключа, но *до* отправки, этот день пропадёт навсегда. Хорошее решение —
> ставить `status = sent` только после успеха, а повторной попытке разрешать подобрать строки в `pending`. Попроси
> агента объяснить этот компромисс — это, кстати, классический вопрос на собеседовании.

## Мини-тест

1. Cron `0 7 * * *`, ты живёшь в UTC+3. Во сколько по-твоему он сработает?
2. Из-за повтора задача отработала дважды. Как не отправить два сообщения?
3. `robots.txt` запрещает страницу, которая тебе нужна. Что делаешь?
4. Запуск по расписанию в GitHub Actions опоздал на 12 минут. Это баг?

> **Ответы:**
>
> 1. В 10:00 по твоему времени: cron живёт по UTC.
> 2. Ключ идемпотентности на запуск (например, дата) с ограничением уникальности; если ключ уже есть — пропустить.
> 3. Не парсить. Искать API, RSS или написать владельцу сайта.
> 4. Нет, под нагрузкой такие запуски задерживаются. Если время критично — cron в Workers.
