Пользователи говорят тебе важное в случайных местах: в личке, в комментариях под вчерашним постом, вздохом, пока ты
смотришь, как они пользуются приложением. К пятнице почти всё это теряется. Сегодня строишь трубопровод: на входе
отзыв, на выходе задача на GitHub, которую агент превращает в пул-реквест, а ты проверяешь и вливаешь.

## Сортировка, как у продакта

**Триаж** — это сортировка входящего по тому, что с ним делать, как в приёмном покое. Для каждого отзыва спроси:

1. **Какой это тип?** `bug` (что-то сломано), `ux` (работает, но непонятно), `idea` (новая функция), `question`
   (возможно, у тебя непонятный текст — это `ux` под прикрытием).
2. **Скольких людей задевает и насколько больно?** Баг в регистрации важнее опечатки в FAQ.
3. **Насколько большое исправление?** Маленькое, среднее, большое.

Первым делом — **важное и маленькое**. Большие идеи — в метку `later`, без чувства вины. И слушай проблему, а не
предложенное решение: «сделайте выгрузку в Excel» может значить «мне каждую пятницу нужно отправить отчёт
бухгалтеру», и тогда лучше автоматическое письмо по расписанию из дня 31.

Хорошая задача содержит: что произошло, чего ждали, шаги или скриншот, страницу или адрес и кто сообщил (никаких
личных данных в публичном репозитории).

## Шаг за шагом

### 1. Кнопка отзыва → задача (30 мин)

Безопасная схема: браузер отправляет отзыв на **твой** сервер, а сервер создаёт задачу токеном, который никогда не
покидает сервер. Создай на GitHub **fine-grained-токен** (`personal access token`) только для репозитория приложения и только с
правом `Issues: Read and write`, положи его в секреты как `GITHUB_TOKEN_ISSUES`.

```text
Цель: кнопка отзыва в приложении, которая создаёт задачу на GitHub.
Контекст: наше приложение (фронтенд на React + Vite, API на Cloudflare Workers + D1). Репозиторий <owner/repo>. Токен в GITHUB_TOKEN_ISSUES.
Ограничения:
- Небольшая кнопка «Отзыв» на каждой странице открывает диалог: тип (ошибка / непонятно / идея), текст (10–1000 символов). Скриншотов в v1 нет (картинку к задаче через API GitHub просто так не приложить), хватит адреса страницы.
- POST /api/feedback проверяет ввод, ограничивает частоту (3 в час на пользователя) и через REST API GitHub создаёт задачу: понятный заголовок, текст, адрес страницы, версия приложения, браузер, метки "feedback" и тип.
- В публичной задаче никаких почт и имён; id автора храним в нашей базе вместе с номером задачи.
- Нет токена — отправляем отзыв мне в Telegram (helper из дня 31). Нет и его — сохраняем в базе.
- Доступный диалог: фокус внутри, закрывается по Escape, работает на 390px, в обеих темах. Интерфейс на русском.
Готово, когда: я отправляю отзыв в живом приложении и вижу задачу на GitHub с нужными метками.
```

Отправь один настоящий отзыв сам. Для задания 2 вставь ссылку на задачу.

> **Безопасность:** если репозиторий публичный, всё в задачах тоже публично. Либо держи репозиторий приватным, либо
> перед публикацией вырезай из текста всё, похожее на почту или телефон.

### 2. Собери и рассортируй (15 мин)

Попроси трёх своих пользователей (и всех, кто откликнулся на вчерашний пост) сегодня отправить отзыв через кнопку.
Добавь то, что заметил сам, когда наблюдал за ними. Потом во вкладке Issues расставь метки и выбери **три важных и
маленьких** задачи.

Агент поможет с сортировкой:

```bash
gh issue list --label feedback --limit 30
```

```text
Выше — наши открытые задачи из отзывов. Сгруппируй дубли, предложи для каждой тип и оценку «важность/объём» и три лучших кандидата на сегодня. Каждый выбор объясни одной строкой. Код не меняй.
```

### 3. Три исправления — три пул-реквеста (35 мин)

Одна задача = одна ветка = один пул-реквест (PR). Так каждое изменение маленькое и его легко проверить.

```bash
git switch -c fix/issue-12
```

```text
Цель: исправить задачу №12 на GitHub. Прочитай её: gh issue view 12
Ограничения: меняй только то, что нужно для этой задачи; добавь или обнови тест, который падает до исправления и проходит после; запусти npm test и npm run build. Потом закоммить, запушь ветку и открой PR через gh pr create.
В описании PR: что поменялось, как проверить, и строка "Fixes #12".
Готово, когда: PR открыт, CI зелёный.
```

Перед слиянием проверь каждый PR: прочитай дифф во вкладке **Files changed**, стяни ветку и попробуй руками, посмотри на CI.
Агент тронул посторонние файлы — попроси откатить. Влей и посмотри, как `Fixes #12` сам закрывает задачу.
Повтори ещё дважды. Для задания 3 вставь ссылку на влитый PR (или на все три).

> **Если застрял:** `gh` пишет, что ты не залогинен, — выполни `gh auth login`. Агент «исправил», а баг на месте —
> ответь в той же сессии, что именно видишь, со скриншотом. Не начинай новый чат, который потерял весь контекст.

> **Совет:** Claude Code умеет работать и внутри GitHub Actions — отвечать на `@claude` в комментариях к задачам
> (настраивается командой `/install-github-app` в Claude Code). Пригодится позже, а сегодня делай всё локально, чтобы
> видеть каждый шаг.

### 4. Рефлексия (10 мин)

Напиши 3–5 предложений: какой отзыв тебя удивил, с чем пользователи мучились, а ты не замечал, и что ты скажешь им
теперь, когда всё исправлено. Да, обязательно скажи: «вы просили — готово» удерживает пользователей лучше любой рассылки.

## Готово, когда…

- [ ] Ты объясняешь, что такое триаж и правило «сначала важное и маленькое».
- [ ] Кнопка отзыва создаёт задачу на GitHub с метками (или сообщение в Telegram). Ссылка вставлена.
- [ ] Три настоящих отзыва исправлены, по PR на каждый, с тестами; ссылка на влитый PR вставлена.
- [ ] Рефлексия написана, авторам отзывов сообщили.

Завтра: один агент за раз — это медленно. Запустишь двух параллельно так, чтобы они не мешали друг другу.
