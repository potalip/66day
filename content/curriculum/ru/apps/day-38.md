Вчера ты смотрел, как работает один агент, и ждал. Теперь узкое место — именно ожидание, а не набор кода. Сегодня ты
становишься маленьким тимлидом: два агента, две задачи, одновременно, а твоё внимание уходит туда, где оно нужнее
всего, — на проверку того, что они сделали.

## Worktree, ветки и субагенты

Два агента в **одной папке** — это хаос: правят одни и те же файлы, один гоняет тесты, пока второй на середине
изменения, а `git status` превращается в место преступления. Нужны отдельные рабочие места.

- **Ветка** — отдельная линия истории. Но в одной папке одновременно может быть открыта только одна ветка.
- **git worktree** — вторая (третья, четвёртая…) папка, привязанная к тому же репозиторию, со своей открытой веткой.
  История общая, файлы раздельные. Идеально: по агенту на папку.
- **Субагенты** — помощники, которых агент запускает сам для себя, например чтобы поискать по коду или проверить дифф,
  каждый со свежим контекстом. Claude Code их поддерживает, у других агентов есть похожие механизмы. Это для поиска и
  ревью внутри одной задачи, а worktree — для действительно разных задач.

Аналогия: worktree — это два рабочих стола с двумя копиями одного чертежа. Субагенты — стажёры, которых ведущий
инженер отправляет в архив.

## Шаг за шагом

### 1. Выбери две задачи, которые не столкнутся (10 мин)

Из вчерашнего списка выбери две задачи про **разные части** приложения: например, одну про текст или вёрстку и одну
про API или данные. Спроси себя: будут ли оба изменения править один и тот же файл? Если да — выбери другую пару.

### 2. Создай два worktree (10 мин)

Из основной папки проекта:

```bash
git switch main && git pull
git worktree add ../myapp-issue-21 -b fix/issue-21
git worktree add ../myapp-issue-22 -b fix/issue-22
git worktree list
```

В каждой новой папке нужны свои зависимости и локальные настройки:

```bash
cd ../myapp-issue-21 && npm install && cp ../myapp/.dev.vars .dev.vars
```

(Со второй папкой то же самое. Файлы с локальными секретами копируй руками: они в `.gitignore`, git их не перенесёт.)

### 3. Два агента, два терминала (35 мин)

Открой два окна терминала (или две вкладки, или две сессии в десктопном приложении), по одному на worktree, и в каждом
запусти агента. Каждому — полное и самодостаточное задание:

```text
Цель: исправить задачу №21 на GitHub (прочитай: gh issue view 21).
Контекст: ты работаешь в git worktree на ветке fix/issue-21. Параллельно в другой папке другой агент делает
другую задачу; не обращай на него внимания, но не выходи за пределы этой папки и этой задачи.
Ограничения:
- Трогай только файлы, нужные для этой задачи. Никаких обновлений зависимостей и переформатирования остального.
- Если запускаешь dev-сервер — на порту 5174 (у второго агента 5175).
- Добавь тест, который падает до исправления. Запусти npm test и npm run build.
- Закоммить, запушь и открой PR через gh pr create: что поменялось, зачем, как проверить, "Fixes #21".
Готово, когда: PR открыт, CI зелёный. Потом остановись и подведи итог в трёх строках.
```

Пока они работают, не стой над душой. Раз в несколько минут загляни в каждый терминал, ответь на вопросы, одобри
команды. Это и есть новый навык: держать в голове два контекста, не делая работу за них. Для задания 2 вставь
ссылки на оба PR.

> **Если застрял:** «port already in use» — оба dev-сервера хотят один порт, раздай им разные. Локальная база во втором
> worktree пустая — так и должно быть: прогони там миграции (`npm run db:migrate:local` или аналог). Агенты всё-таки
> столкнулись? Влей один PR, а второго агента попроси выполнить `git fetch origin && git rebase origin/main` и разрулить конфликты.

### 4. Ревью уровня сеньора (25 мин)

Агенты быстро пишут правдоподобный код. Правдоподобный — не значит правильный. Сеньор проверяет по порядку:

1. **Решает ли это задачу?** Стяни ветку, запусти, воспроизведи исходный баг — его больше нет.
2. **Границы**: изменено что-то, о чём задача не просила? Посторонние файлы, переименования, новые зависимости?
3. **Тесты**: новый тест правда падает без исправления? (Откати исправление локально и запусти.)
4. **Пограничные случаи и безопасность**: пустой ввод, чужие данные, обработка ошибок, секреты.
5. **Читаемость**: поймёшь ли ты это через три месяца?

Выбери один из двух PR и оставь **3 комментария** в интерфейсе ревью GitHub (Files changed → клик по строке →
комментарий). Каждый — конкретный и с понятным действием, например:

> «Запрос фильтрует только по `item_id`. Добавь фильтр по `user_id`, иначе любой пользователь прочитает чужую
> запись. И тест с двумя пользователями».

Потом верни комментарии агенту: в его сессии выполни `gh pr view 21 --comments` и попроси учесть. Когда всё
правильно — влей и прибери за собой:

```bash
git worktree remove ../myapp-issue-21
git branch -d fix/issue-21
```

Для задания 3 вставь свои три комментария.

## Мини-тест

1. Обе задачи меняют `api/items.ts`. Параллельно или по очереди?
2. Задача — «выяснить, почему регистрация тормозит». Два агента или один?
3. Одна задача добавляет миграцию базы, другая меняет код вокруг той же таблицы. Параллельно?
4. Чем worktree отличается от субагента?

<details><summary>Ответы</summary>

1. По очереди. Один файл — значит конфликты слияния и работа каждого агента с устаревшим кодом.
2. Один. Расследованию нужна цельная картина; делить можно потом, когда понятно, что чинить. (Субагент для поиска по коду — нормально.)
3. Нет. Изменения схемы расходятся кругами по всему коду; сначала влей миграцию, потом остальное.
4. Worktree — отдельная папка и ветка для отдельной задачи; субагент — помощник, которого агент запускает внутри своей задачи со свежим контекстом.

</details>
